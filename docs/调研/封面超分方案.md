# 展示页封面轻量超分方案调研

取证日期：2026-10-22。状态：研究建议，尚未实现、未进行 WhaleDeck 实机性能或画质测试。本文保存候选方案和取舍证据，不定义应用当前行为，也不替代现有产品、架构、数据和接口规范。

## 初步结论

用户进一步明确：由用户选择哪些封面做超分；超分辅助程序只在处理期间运行；可以增加包体，也可以等待较长时间，但要有明确进度；可考虑提供效率与质量两档。

据此，**优先评估独立 ncnn 辅助进程，逐张手动生成、保存增强结果，处理结束后退出进程，平时直接显示图片**。选型重点是画质、可信进度、取消能力和任务结束后的资源释放。这是一条集成路线建议，尚不能据此确定画质与速度最好的模型。

### 两档方案的验证顺序

| 建议档位 | 首轮候选 | 选择理由与限制 |
|---|---|---|
| 效率档 | `realesr-animevideov3`，按展示需求选择原生倍率，优先测试 2× | 官方定位为动漫 XS 模型，现成 ncnn 工具支持。用于静态封面仍需验证；该工具仅支持 GPU。效率是否优于其他候选，以同一目标输出尺寸的实测为准。[E1][E4] |
| 质量档 | 静态二次元先测 `RealESRGAN_x4plus_anime_6B`，同时与 Real-CUGAN 保守 2×对照 | 前者是官方针对动漫图片/插画优化的模型，ncnn 名称为 `realesrgan-x4plus-anime`；后者已有小型模型和 CPU / Vulkan 工具。质量档应由实际封面盲测选出，不能只凭模型更大、处理更久或倍率更高决定。[E1][E4][C2] |
| 照片、3D 宣传图的质量候选 | `RealESRGAN_x4plus`；后续再测 `realesr-general-x4v3` | x4plus 已有现成 ncnn 工具支持；general 小模型需先解决转换与一致性验证。首版可以先明确支持二次元封面，不把动漫模型无条件用于所有素材。[E1][E4] |

两档应尽量复用一个执行器，由预设选择模型与参数；无需各打包一套完整运行时。展示倍率由容器与设备像素密度决定，不能简单把“2×”等同效率档、“4×”等同质量档。质量候选如果没有稳定的主观改善，就不应仅为了凑两档而发布。

原先偏极小体积的 FSRCNN、FSR 1 / CAS 和浏览器实时着色器路线降为备选。仍不建议首版引入 Python / PyTorch 运行环境、云端推理或视频时域重建链路。模型权重在磁盘中长期保留，处理进程及其推理状态按任务创建和销毁。

## WhaleDeck 的接入条件

当前边界以 [系统架构](../系统架构.md)、[数据模型](../数据模型.md)、[界面与交互](../界面与交互.md) 和 [前端实现](../前端实现.md) 为准。以下是读取代码后的选型分析：

| 观察位置 | 对方案选择的影响 |
|---|---|
| [`GameDetail.tsx`](../../src/components/GameDetail.tsx) 的全幅 `<img>` 使用 `object-cover`，并叠加渐变遮罩 | 不只看图片宽度，要按容器宽高、裁切和屏幕像素密度决定放大需求；被遮罩覆盖的细节改善未必可见。 |
| [`store.rs`](../../src-tauri/src/store.rs) 的手选图片导入复制原文件；[`meta.rs`](../../src-tauri/src/meta.rs) 的 Bangumi 已取 `images.large` | 目前未发现导入时主动降采样；优先核查原始素材质量。不要把更大 URL 字符串或更大输出像素数当成细节提升的证据。 |
| [`assets.ts`](../../src/lib/assets.ts) 管理解码与启动资源等待；[`useAssetUrl.ts`](../../src/lib/useAssetUrl.ts) 隔离迟到资源响应 | 推理不宜进入启动等待链路。页面先显示原图，缓存可用后再替换，仍需校验当前封面和请求是否匹配。 |
| [`Cargo.toml`](../../src-tauri/Cargo.toml) 未集成神经网络推理与通用图片解码库；[`tauri.conf.json`](../../src-tauri/tauri.conf.json) 未配置超分资源 | 除模型外，还需计算原生代码、解码/编码、模型资源和许可声明的增量；现有 `png` 依赖不能代替 JPEG / WebP 等输入解码链路。 |

对于居中 `object-cover`，设原图为 `W×H`、实测容器为 `Cw×Ch` CSS 像素、设备像素比为 `D`，达到当前显示物理像素密度所需的线性倍率约为：

```text
r = max(Cw × D / W, Ch × D / H)
```

`r ≤ 1` 时通常无需增加分辨率；`r > 1` 才进入倍率选择。此式只衡量采样密度，不衡量原图模糊或压缩程度。根据界面文档中的窗口和侧栏规格，示例容器可近似为 1022×820：600×850 的竖图在 D=1 时约需 1.70×，D=2 时约需 3.41×。正式实现应读取容器与实际 D，不能硬编码这个例子。超分不会扩大原画的构图范围，也不能补回 `object-cover` 裁掉的内容。

## 神经网络候选

“轻量”需要同时衡量模型、推理运行时、临时图像、峰值内存和首次调用开销。下表的模型文件尺寸不是应用最终安装包增量；尺寸来自项目发布 API 或固定提交的文件树。MB 按 1,000,000 字节计算。

| 候选 | 已核验的能力与体积 | 对封面的初筛判断 | 主要限制 |
|---|---|---|---|
| Real-ESRGAN `realesr-general-x4v3` | 官方定位为通用场景小模型，明确说明显存与时间消耗较少，但去模糊、降噪能力较弱。v0.2.5.0 `.pth` 为 **4,885,111 B（4.89 MB）**。原模型原生 4×，其他输出倍率由后处理缩放实现。[E1][E2][E3] | 适合进入混合照片、插画、游戏宣传图封面的主候选；此判断是基于模型定位的推断，需通过实际封面对照确认。 | 不能将 `.pth` 直接交给 ncnn。官方 ncnn 工具 README 没有列出该模型，需自行转换及核对推理和后处理。可调降噪的官方 Python 实现会混合强、弱降噪两份权重；弱降噪模型另为 **4,885,111 B**，两份原始权重合计 9.77 MB，并非单个 4.89 MB 模型就拥有完整滑杆能力。[E2][E3][E4] |
| Real-ESRGAN `realesr-animevideov3` | 官方定位为动漫视频 XS 模型。v0.2.5.0 `.pth` 为 **2,504,012 B（2.50 MB）**；官方 ncnn 工具直接支持名称和 2×、3×、4×模型选择。[E1][E2][E4][E5] | 可作为低成本动漫封面的验证候选。 | 视频模型用于静态宣传插画需要独立确认；上游另有面向动漫插画的 `RealESRGAN_x4plus_anime_6B`，不能仅凭名称认定视频小模型画质最佳。ncnn 格式的实际单模型大小未取得可靠证据。[E1] |
| Real-CUGAN `models-pro/up2x-conservative` | 官方面向动漫图像，提供保守、无降噪和不同降噪模型。所查 ncnn 2×保守模型 `.bin` **2,573,648 B** + `.param` **4,765 B**，合计约 **2.58 MB**。工具支持 CPU `-g -1`、Vulkan、分块处理。[C1][C2][C3] | 动漫封面建议与动漫视频小模型并列进行 2×对照，先测保守模型。 | 不应作为照片封面的默认模型。不同降噪和倍率是不同权重，全部内置会累加包体；同步模式、分块接缝和虚化区域保留需要实测。上游自身的对比表不构成 WhaleDeck 环境的性能或画质结论。[C1][C2] |
| waifu2x `upconv_7` / `cunet` | 原项目支持动漫和照片。ncnn 的 `upconv_7` 动漫或照片单个 2×模型 `.bin` **1,106,248 B** + `.param` **1,047 B**，约 **1.11 MB**；`cunet` 2×单模型约 **2.78 MB**。工具支持 Vulkan 和 CPU。[W1][W2][W3] | `upconv_7` 可作为更轻的神经网络基线；须区分动漫与照片权重。 | 降噪等级和画风对应不同模型。README 的 GTX 1070 历史速度表只适用于其输入、驱动和配置，不能据此承诺当前集显、冷启动或整条封面链路耗时。[W2] |
| FSRCNN / ESPCN | 所查 OpenCV GSoC 实现提供 2×、3×、4× TensorFlow `.pb`。FSRCNN 2× **38,973 B**，FSRCNN-small 2× **9,595 B**；ESPCN 2× **86,446 B**。这些是包含计算图的模型文件大小。[F1][F2][F3][F4] | 如果模型预算必须低于 1 MB，值得保留为 CPU 方向的对照基线。 | 小文件不代表无需运行时。此 FSRCNN 实现将原论文转置卷积替换为子像素层；不能把原论文的速度结论直接套到该实现。它们未被核验为针对严重压缩、模糊游戏封面的盲修复模型，转换为 ncnn / ONNX 后仍需复核输入、输出和画质。[F1][F2][F5][F6] |
| Anime4K | 官方提供可实时运行的动漫放大、去噪算法和 shader；当前说明的主要优化目标是原生 1080p 动漫视频到 4K。[A1] | 仅保留为动漫展示效果路线的备选，不作为混合封面的第一选择。 | 官方明确说明不针对低分辨率、严重退化图像，且不能替代这类场景的 SRGAN。已有 GLSL/mpv shader 不能直接当成浏览器 WebGPU 或 Rust 组件；移植、纹理处理和输出缓存均需工程验证。[A1] |

### 倍率与画质判断

原始素材的类型、压缩方式和实际展示倍率比“模型属于 AI 超分”更能影响结果。对混合封面，目前只能推荐验证 `general-x4v3`，不能宣布它已胜过其他方案。对动漫封面，`Real-CUGAN` 保守 2×与 `animevideov3` 2×具有明确的试验价值。FSRCNN、ESPCN 和 `waifu2x-upconv_7` 可用来检验是否值得为更复杂模型增加成本。

官方 Real-ESRGAN Python 实现中的 `outscale=2` 与原生 2×网络不是同一计算路径：`general-x4v3` 的网络倍率仍为 4，输出再缩到目标倍率；`animevideov3` 的官方 ncnn 工具则按倍率加载 `-x2/-x3/-x4` 模型。评估时必须记录实际路径，不能仅记录 UI 中的“2×”。[E3][E4]

超分输出包含模型推断出的细节。小字、Logo、像素画、摄影颗粒、原本有意虚化的背景需要单独检查；“更锐”不能直接替代“更忠实”的验收。以上是本次方案评估建议，并非已观察到的 WhaleDeck 缺陷。

## 运行时：ncnn 的已核验范围

ncnn 官方说明无第三方推理运行时依赖，提供 CPU 与 Vulkan GPU 后端，并可通过 pnnx 等工具转换 PyTorch / ONNX 模型。其 C++ / C API 和模型内存加载方式适合放在桌面应用后端；与 Rust/Tauri 如何连接属于集成设计，尚未验证。[N1]

必须区分“ncnn 框架有 CPU 后端”与“某个现成超分程序有 CPU 回退”：所查 `realcugan-ncnn-vulkan` 和 `waifu2x-ncnn-vulkan` 的帮助明确支持 `-g -1`；所查 `Real-ESRGAN-ncnn-vulkan` 的 `main.cpp` 会拒绝小于 0 的 GPU ID。因此不能给现成 Real-ESRGAN 程序承诺 CPU 兜底。[E4][C2][W2]

现成命令行工具能降低验证成本，但不应直接采用完整模型包代表最终方案。Real-ESRGAN 主仓库 v0.2.5.0 的 Windows ZIP 为 **45,474,481 B**，ncnn 仓库另一发布 v0.2.0 的 Windows ZIP 为 **2,159,606 B**；它们是不同发布的压缩包，尚未核验内部文件集合，不能直接比较运行时大小，更不能等同最终应用包体增量。[E2][E6]

本次未运行任何候选，以下数据均未知：自定义裁剪后的 ncnn DLL/静态库大小、Vulkan 驱动覆盖率、集显和独显冷启动耗时、转换后模型大小、峰值内存/显存、每张真实封面的耗时。官方“快”“低内存”和旧硬件表不能补齐这些缺口。

### 其他运行时与空间算法

| 路线 | 已核验事实 | 本次判断 |
|---|---|---|
| ONNX Runtime 原生 + DirectML | DirectML EP 使用 DirectX 12，要求可用的 DX12 设备；官方文档说明 DirectML 已进入持续维护，新功能转向 Windows ML。[R1] | 可作为 Windows GPU 路线的备选，尤其在 Vulkan 覆盖不理想时。仍需 ONNX 转换、算子检查和正确的会话配置，不能按“Windows 自带”推导零包体。 |
| 新 Windows ML | 官方列出内置 CPU / legacy DirectML；可动态下载的厂商 EP 有 Windows 11 24H2 或以上及设备、驱动条件。[R2] | 暂不作为 Windows 10/11 离线统一路线的首选；并非所有 Windows ML 能力都要求 24H2，要区分内置与动态 EP。 |
| ONNX Runtime Web + WebGPU / WASM | ORT Web 可离线运行；GPU 后端只支持部分 ONNX 算子，WASM 是 CPU 方向。WebGPU 需要明确选择后端。[R3][R4] | 可以利用现有 WebView，但不能由 Edge 支持推导所有用户的 WebView2、驱动与设备都可用。还需探测、Worker、资源本地打包、输出落盘和失败处理；不预设其安装体积或速度优于原生。 |
| 裁剪 ONNX Runtime | 官方支持按模型所需算子构建较小运行时。[R5] | 是后续优化手段，首轮不承诺具体 MB；更换模型也可能需要重建与重新验证。 |
| FSR 1 EASU + RCAS / CAS | FSR 1 是空间放大，两阶段分别处理边缘放大与锐化，无需历史帧或运动向量；CAS 支持锐化与可选缩放，二者为 MIT。[S1][S2] | 适合作为无需模型权重的备选与对照。官方提供图形着色器，不是 `<img>` 的 CSS 选项；要么移植 WebGL/WebGPU，要么在后端构建离屏图形管线，仍有工程和兼容性成本。 |

FSR 1 本次固定提交中的 `ffx_a.h` 为 181,915 B、`ffx_fsr1.h` 为 60,310 B，合计约 0.24 MB **源代码**；这不是编译产物或安装包增量。AMD 还提供能处理静态图的 CLI 供验证，但不应为了两个算法默认打包完整 SDK。[S2][S3]

## 建议的最小产品与处理链路

本节为后续实现提案，字段、命令和界面尚未确定；实施前应先更新文档索引指向的各份权威规范，不直接把本报告当成已批准的接口。

1. **用户可选、默认保留原图**：先支持当前封面增强和原图对照、取消、恢复原图；评估效率与质量两档，避免用户必须理解推理框架。
2. **先显示，再生成**：原图或已存在缓存立即展示；用户明确点击生成后进入后台单任务队列。打开页面、切换项目和启动游戏不产生推理任务；失败或缓存缺失时保持原图，由用户选择是否重新生成。
3. **原图与派生图分离**：保留 `coverFile` 的原始语义，提案中的派生缓存放在独立目录；不把它直接塞入现有 `covers/`，因为整库导出会复制其中的全部文件。开关和缓存索引是否需要持久化应在数据模型中另行设计。
4. **以内容使缓存失效**：缓存键至少关联原图内容哈希、模型及权重版本、参数和输出尺寸档位；不能只用游戏 ID 或原文件名，联网替换封面可能复用文件名。写临时文件后原子发布，防止半张图片被读取。
5. **控制资源与生命周期**：对解码尺寸、输出像素、分块大小和并发数设边界；输入文件体积小不代表解码后内存小。原图更换后旧任务不得覆盖新结果；取消是否能终止计算需随后端验证。设置缓存容量、清理和重建策略。
6. **按任务启动独立辅助程序**：Rust 负责调度，前端只拿状态与资源 URL。Tauri 官方支持用 `externalBin` 打包按目标架构命名的辅助程序，模型作为资源处理。每次生成才启动，成功、失败、取消或应用退出时均要回收该任务进程；首版串行处理。模型加载与冷启动开销计入用户等待，不在后台常驻预热。[T1]

缓存首次生成仍需推理；缓存命中时不再推理。神经网络倍率过高会增加输出像素、编码与内存开销，例如 4×输出像素数是原图的 16 倍。因此应根据展示目标设输出上限，而非无条件把所有封面放大 4×。

### 操作与进度的提案

选中一张封面后，用户选择效率或质量并点击生成。生成期间保持原图可见，可看到当前阶段、推理阶段进度、已用时间和取消入口；生成成功后可切换原图与增强图。再次切换图片只读已保存结果，不启动辅助程序；更换原图或档位后重新生成才创建新任务。

建议将进度分为“读取图片 → 加载模型 → 预处理 → 超分处理 → 保存图片 → 完成”。有可靠计数的阶段展示已完成工作与总量；没有可靠计数的阶段展示阶段名称、忙状态和已用时间。推理进度达到 100% 仍须继续显示保存阶段，输出成功发布后才宣布完成。首轮不显示未经校准的剩余时间，也不按计时器伪造总百分比。

**现成工具的输出需要适配，不能直接承诺完整进度条。** 所查 Real-ESRGAN ncnn 会向 stderr 输出分块编号百分比，首条为 0%，最后一块小于 100%，每张图重置；部分路径在 GPU 工作实际等待完成之前输出，不能直接解释为已完成推理。所查 Real-CUGAN 的模型实现没有对应百分比输出，`-v` 是保存成功后的完成信息。[P1][P2]

Real-CUGAN 的部分同步路径在最终重建前还会计算特征和全局统计，进度适配必须覆盖这些阶段；只统计最后一次分块循环会漏掉前段计算。所查工具的部分保存失败路径仅打印错误，因此还需补充明确的失败事件或错误返回，宿主不能只凭退出码判成功。[P1][P2]

因此推荐把执行器进度适配列为首轮验证的一部分：定义结构化的阶段、可靠完成计数、失败与完成事件，由 Rust 转发界面。若修改原生代码，优先在既有可确认的完成边界上报，避免为了每个进度点强行增加 GPU 同步；读取完整事件、结束状态和输出有效性后才接受结果。取消需要终止实际工作进程并清理临时输出，不能只关闭进度界面。尚未实现或验证这些能力。

两种工具均有 TTA（测试时增强）选项，所查实现对每块执行八个变换方向的网络推理，因此网络评估次数约为普通模式的八倍；不代表端到端耗时恰好八倍，也不保证每张封面更好。首轮先比较模型，不默认用 TTA 定义质量档。[P1][P2]

## 许可证与分发边界

模型、推理程序、推理框架、图像编码库和展示样例是不同来源，不能用某一个仓库的 MIT 标签覆盖整条分发链。

## 建议的候选验证方法

以下为后续试验建议，尚未执行：

1. 先抽取真实封面，覆盖动漫插画、真人照片、3D 游戏宣传图、文字/Logo、像素画、压缩噪声与虚化背景。使用同一目标像素尺寸、裁切和显示密度比较，而非只对比原图与 4×导出图。
2. 保留当前显示结果，以及高质量普通缩放作为基线；效率候选先测 `animevideov3`，质量候选比较静态动漫 6B 和 Real-CUGAN 保守模型，混合素材另测通用 x4plus。需要时再验证 general 模型转换；各档统一到同一展示尺寸比较。
3. 同时记录冷启动和热调用的端到端耗时，包含读图、解码、模型/管线初始化、计算、编码、缓存及页面显示；记录峰值内存/显存和安装包实际增量。
4. 在至少一台集显、一台独显及 GPU 后端不可用的环境验证。无有效超分结果时保持原封面显示，避免让推理成为页面出现的前置依赖。
5. 验证效率与质量两档是否形成有意义的取舍；两档均需校验真实进度、取消终止、任务结束后无残留工作进程，以及缓存显示不再启动进程。首轮无需内置全部倍率、全部降噪等级或整套模型动物园。
