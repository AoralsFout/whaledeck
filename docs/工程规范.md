# 工程规范

> 本文定义开发命令、代码与注释规范、测试门槛、Git 提交、版本发布与 `gh` 使用。
> 文档本身的维护规则见 [docs/文档索引.md](文档索引.md)；产品范围见 [产品定义.md](产品定义.md)。

---

## 1. 环境与命令

前置：Node.js 20+、pnpm、Rust（MSVC 工具链）、WebView2（Windows 10/11 自带）。

| 命令 | 作用 |
|---|---|
| `pnpm install` | 安装前端依赖 |
| `pnpm dev` | 只启动 Vite（浏览器预览） |
| `pnpm tauri dev` | 开发模式（Vite + Tauri 热更新） |
| `pnpm build` | `tsc --noEmit` + Vite 构建 |
| `pnpm test` | Vitest（node 环境） |
| `pnpm tauri build` | 打包 NSIS 安装程序 |
| `cd src-tauri && cargo test` | Rust 单测 |
| `cd src-tauri && cargo fmt --check` | 格式检查 |
| `cd src-tauri && cargo clippy -- -D warnings` | 静态检查（提交前建议） |

约束：

- Vite 端口固定 `1420`，`strictPort: true`；不要改端口，Tauri 配置依赖它。
- `vite.config.ts` 忽略 `**/src-tauri/**`，避免 cargo 构建时 Node 监听器 `EBUSY`。
- `pnpm-workspace.yaml` 放行 esbuild 构建脚本；pnpm 11+ 默认拦截依赖脚本。
- 前端无 ESLint/Prettier 配置，类型检查（strict）是硬门槛；Rust 以 `fmt` + `clippy` 为准。

## 2. 代码规范

### 2.1 文件头文档注释（强制）

每个源码文件顶部必须说明「这个文件负责什么、边界在哪、对应哪份文档」。注释不写实现流水账。

**TypeScript / TSX**

```ts
/**
 * @file 视图过滤与选择规则（纯函数）。
 *
 * 这里只做内存中的筛选/排序/选择，不发请求、不读写磁盘。
 * 对应文档：docs/前端实现.md「视图规则」。
 */
```

**Rust**

```rust
//! 数据仓库：JSON 原子写入、备份与损坏回退。
//!
//! 对应文档：docs/后端实现.md「存储实现」、docs/数据模型.md「写入策略」。
```

**Python**

```python
"""生成应用图标源图（assets/icon-source.png）。

仅用于开发期重新生成图标，不参与运行时。
"""
```

规则：

- 文件头写**职责 + 不做什么 + 文档链接**，新增/移动文件时同步更新。
- 测试文件也要写：说明覆盖的行为域（如「游戏写入与批量加入」）。
- 配置/脚本文件（`vite.config.ts`、`scripts/*.py`）至少写一段用途说明。
- 文件头不写作者、日期、版本号；这些由 Git 记录。

### 2.2 关键函数注释（强制）

以下位置必须有注释，解释**为什么、约束、副作用**，而不是复述函数名：

- 导出的 React 组件与 Hook；
- store 的动作、状态机、请求版本/生命周期逻辑；
- 纯函数中的边界规则（过滤、排序、格式化、路径比较）；
- Rust 的 `#[tauri::command]`、算法函数、锁与写盘路径、Windows API 调用；
- 任何「看起来可以简化，但不能」的代码（竞态、兼容、Windows 行为）。

```ts
/** 只有一个详情页生命周期内有效的备份状态；卸载后丢弃迟到响应。 */
export function createSaveBackups(gameId: string, deps: SaveBackupsDependencies) { … }
```

```rust
/// 先写盘再替换内存：写失败时保留旧记录，调用方可以安全重试。
fn save_game_record(state: &AppState, mut game: Game) -> Result<Game, String> { … }
```

不要求给 getter、简单映射、显而易见的 JSX 写注释。

### 2.3 TypeScript

- `strict` + `noUnusedLocals/Parameters`；不用 `any`，外部数据在边界处收窄。
- 与 Rust 对齐的类型放 `src/types.ts`；IPC 调用只放 `src/lib/ipc.ts`。
- 组件不直接 `invoke`；异步动作优先放 store，组件只处理本地 UI 状态。
- 纯逻辑放 `lib/` 或 store 工厂，便于 Vitest 覆盖。
- 路径比较统一用 `gamePathKey`，不要各写一套大小写/分隔符处理。
- 时间/时长/大小统一用 `format.ts`，不在 JSX 里手写单位。

### 2.4 Rust

- 遵循 `cargo fmt`；`clippy -D warnings` 作为目标。
- 命令错误统一 `Result<T, String>`，文案是可直接展示的中文。
- 锁的持有范围尽量短；写盘前先构造候选数据，成功后再替换内存。
- Windows 路径用 `Path` / `PathBuf`；启动参数先拆分再逐个传，禁止拼 shell 字符串。
- 新增 Windows API 时在 `Cargo.toml` 的 `windows-sys` features 中显式开启。
- 文件读写错误要带路径与原因，方便用户自查。

### 2.5 文案

- 简体中文；错误说明「发生了什么 + 可以怎么做」。
- 不出现内部错误码、英文异常原文作为唯一信息（可附在冒号后）。
- 单位明确：分钟、小时、MB、`HH:MM:SS`。

## 3. 测试与验证门槛

### 3.1 提交前

- [ ] `pnpm build` 通过（含 `tsc --noEmit`）。
- [ ] `pnpm test` 通过。
- [ ] `cargo test` 通过（涉及 Rust 时）。
- [ ] `cargo fmt --check` 通过（涉及 Rust 时）。
- [ ] 手工验证受影响界面（至少桌面 1280×820 + 窄屏 375px，若涉及 UI）。

### 3.2 测试分工

- 纯函数、store 状态机 → Vitest（node 环境，不渲染组件）。
- 存储、启动判断、zip、封面评分、元数据解析 → Rust 单测 + `tempfile`。
- 涉及真实网络 → `#[ignore]` 冒烟测试，手动执行，不进常规流程。
- 涉及真实进程/窗口/文件对话框 → 手工验收，不写成脆弱的自动化。

测试文件与被测模块同名（`*.test.ts` / `#[cfg(test)] mod tests`），新增行为优先补对应文件，而不是新建大杂烩测试。

## 4. 文档维护

1. 需求/行为变更：先改 [docs/文档索引.md](文档索引.md) 权威矩阵指向的主题文档，再改代码。
2. 一个事实只写一次；需要时用相对链接。
3. 历史只写进 [版本记录.md](版本记录.md)。
4. 字段变更同步 [数据模型.md](数据模型.md)；命令变更同步 [接口契约.md](接口契约.md)。
5. 界面尺寸/时序变更同步 [界面与交互.md](界面与交互.md)。
6. 新术语先补 [GLOSSARY.md](../GLOSSARY.md)。
7. 代码文件头的「对应文档」随文档拆分同步更新。

## 5. Git 规范

### 5.1 语言

**整个 Git 流程使用中文**：提交标题与正文、分支说明、PR 标题/描述、发布说明、合并说明。

Conventional Commits 的 **type 前缀保留英文**，其余用中文：

```text
<type>(<scope>): <中文摘要，不超过 50 字>

<为什么改、改了什么、影响范围；可多行>

<关联 issue / PR（可选）>
```

示例：

```text
docs: 拆分设计方案为按职责划分的文档体系

将 641 行的设计方案拆为产品、架构、数据、IPC、前后端、UI、工程与历史文档，
建立单一权威来源矩阵；旧文件保留为跳转入口。
```

```text
style(code): 为前端源码补充文件头与关键函数注释

统一 @file 说明职责与对应文档，并补充 store 生命周期、批量加入、
资源加载等关键逻辑的注释；不改变运行时行为。
```

类型：

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复 |
| `refactor` | 不改变行为的重构 |
| `docs` | 文档 |
| `style` | 格式/注释/空白（不改逻辑） |
| `test` | 测试 |
| `chore` | 构建、依赖、杂务 |

### 5.2 粒度

- 一个提交只做一件事：文档拆分、注释补充、行为修复不要混在一起。
- 文档与对应代码行为变更可以同一提交，但必须说明。
- 不提交 `node_modules/`、`dist/`、`src-tauri/target/`、`release/`、日志与临时文件。
- 提交前 `git diff --check`，避免行尾空白。
- 不提交自动生成的 `src-tauri/gen/`（已忽略）。

### 5.3 分支

- `main` 保持可构建。
- 功能分支用 ASCII：`feat/xxx`、`fix/xxx`、`docs/xxx`；分支说明与提交正文用中文。
- 合并前自测；合并提交信息说明范围与验证。

## 6. 版本与发布

### 6.1 版本号同步

一次版本提升必须同时修改：

1. `package.json` 的 `version`
2. `src-tauri/Cargo.toml` 的 `version`
3. `src-tauri/tauri.conf.json` 的 `version`
4. `src/components/SettingsPanel.tsx`「关于」中的版本文案
5. 必要时 README 的安装包文件名

否则会出现安装包、窗口标题、关于页版本不一致。

### 6.2 打包

```bash
pnpm tauri build
```

- 产物：NSIS 安装包，按当前用户安装（`installMode: currentUser`），简体中文。
- 便携版：取 `src-tauri/target/release/WhaleDeck.exe` 与必要资源打包为 zip；`release/` 不提交。
- 构建配置：release 开启 LTO、`opt-level = "s"`、strip、`panic = "abort"`。

## 7. GitHub 与 `gh`

仓库：https://github.com/shasha111250/whaledeck

规则：

- **访问 GitHub 统一用 `gh` CLI**。认证由 `gh` 的 keyring 管理，不在命令、脚本、提交里出现 token。
- 需要跨出沙箱访问网络/GitHub 时，也用 `gh`（以及 `git` 通过 `gh` 已配置的凭据），不手工 `curl` 带 token。
- 操作前先确认目标：

```bash
gh auth status
gh repo view shasha111250/whaledeck
git remote -v
git branch --show-current
```

- 从 fork 贡献时，推送目标应是自己的 fork，PR 提交到 `shasha111250/whaledeck`；不要把上游当作默认推送目标。
- 推送、开 PR、发 Release 前确认 remote 与分支。
- 提交信息、PR 标题与正文、Release 说明全部用中文。
- 未经用户明确要求，不执行 `push`、`gh pr create`、`gh release create`、强推或删除分支；本地提交是默认交付。

## 8. 完成定义（DoD）

- 代码可构建、测试通过、无新增警告。
- 文件头与关键函数注释齐全，且指向正确的文档。
- 受影响文档已更新，无重复事实。
- changelog 记录行为变化。
- 提交信息为中文、粒度单一。
- 若涉及 UI，完成 [界面与交互.md](界面与交互.md) 对应验收清单。
